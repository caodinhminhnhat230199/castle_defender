# UI Architecture

## Load When

Use for UMG, CommonUI, HUD, menus, gamepad navigation, UI state, or gameplay-to-UI communication.

## Ownership

Keep gameplay state outside widgets.

Widgets should observe/use view data, not become authoritative gameplay systems.

## CommonUI

Use when the project benefits from:

- input routing
- gamepad-first navigation
- activatable screens
- layered UI stacks
- cross-platform input behavior

Do not add it solely for one simple HUD.

## Communication

Prefer:

```text
gameplay state
→ presentation/view model/controller
→ widget
```

Avoid widgets polling world actors every frame.

## HUD

Frequently updating values should be updated from events or compact view-state changes where practical.

## UI Assets

Avoid hard-reference chains from persistent UI into large gameplay content unless intentional.

## Rule

UI is presentation and interaction, not the owner of core game rules.
